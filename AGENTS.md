# AGENTS.md

## 1. Контекст и границы

### Назначение проекта
Проект реализует внутреннюю систему бронирования переговорных комнат для сотрудников компании. Приложение состоит из backend на ASP.NET Core (Web API) и frontend на React + TypeScript, где пользователи просматривают комнаты, создают/изменяют бронирования и управляют своей учетной записью.

Авторизация построена на cookie-аутентификации с ролями `User` и `Admin`. Администратор управляет комнатами и имеет расширенный доступ к данным бронирований, обычный пользователь работает со своими бронированиями и общим каталогом комнат.

### Основные модули/папки и ответственность
- `Program.cs`: конфигурация ASP.NET Core приложения, DI, cookie-auth, authorization policies, middleware pipeline.
- `Controllers/`: API-контроллеры (`AuthController`, `RoomsController`, `BookingsController`) и HTTP-контракты.
- `Data/Models/`: доменные модели (`User`, `Room`, `Booking`).
- `Data/Services/`: сервисный слой и бизнес-логика (в текущей реализации in-memory хранение на `List<T>`).
- `ClientApp/src/components/`: страницы и UI-компоненты React.
- `ClientApp/src/store/`: Redux Toolkit slices для `auth`, `rooms`, `bookings`.
- `ClientApp/src/types/`: frontend типы доменных сущностей.
- `docker-compose.yml`, `Dockerfile`: контейнеризация и запуск приложения.

### Ключевые сущности и термины (мини-глоссарий)
- `User`: пользователь системы (поля: `id`, `login`, `name`, `role`).
- `Role`: роль доступа (`User` или `Admin`).
- `Room`: переговорная комната (вместимость, локация, описание, удобства, доступность).
- `Booking`: бронирование комнаты на интервал времени (`startDate`-`endDate`) с привязкой к пользователю и комнате.
- `Availability`: проверка пересечения временных интервалов бронирований комнаты.
- `Soft delete booking`: удаление бронирования через `IsActive = false`, а не физическое удаление записи.

### Ограничения: что нельзя менять и почему
- Нельзя ломать публичные API-контракты без явной задачи на миграцию: frontend зависит от текущих маршрутов `/api/auth`, `/api/rooms`, `/api/bookings`.
- Нельзя менять семантику ролей `Admin/User` без синхронного обновления backend authorization и frontend route guards, иначе появятся ошибки доступа.
- Нельзя удалять проверку доступности комнаты при создании/обновлении бронирования: это ключевое бизнес-правило.
- Нельзя вносить опасные изменения в инфраструктуру запуска (`Dockerfile`, `docker-compose.yml`, `Program.cs`) без проверки локального старта приложения.
- Нельзя без отдельной задачи переводить хранение данных с in-memory на БД: это архитектурное изменение с миграциями и влиянием на контракты/тесты.

### Уточняющие вопросы vs допущения
- Агент должен задавать уточняющие вопросы, если требования влияют на API-контракт, безопасность, роли доступа или формат данных.
- Агент может делать разумные допущения для локальных неразрушающих изменений (UI-текст, внутренний рефакторинг, нейминг), но обязан явно перечислить допущения в ответе.

## 2. Требования к результату

### Стиль кода и форматирование
- Backend (.NET/C#):
  - следовать существующему стилю проекта (nullable enabled, async/await, DI через интерфейсы);
  - не добавлять лишние абстракции без необходимости;
  - сохранять читаемые имена и явные проверки входных данных.
- Frontend (React/TypeScript):
  - следовать текущему ESLint + Prettier конфигу в `ClientApp`;
  - функциональные компоненты, Redux Toolkit patterns, строгая типизация TypeScript;
  - избегать `any` без необходимости.
- Форматирование:
  - frontend: `npm run lint` и при необходимости `npm run format` в `ClientApp`;
  - backend: сохранять формат и структуру существующего кода.

### Требования к тестам и проверкам
- Минимум проверок после изменений:
  - `dotnet build` в корне проекта;
  - `npm run lint` в `ClientApp`;
  - `npm run build` в `ClientApp` при изменениях frontend-сборки или маршрутизации.
- Для бизнес-логики бронирования обязательно проверять сценарии:
  - создание валидного бронирования;
  - запрет пересекающихся бронирований;
  - права доступа на изменение/удаление бронирования.
- Если полноценные автотесты отсутствуют, агент должен выполнить минимум ручной smoke-check и описать результаты.

### Формат ответа ИИ
- План действий:
  - краткий список шагов до внесения изменений.
- Изменения в коде:
  - список файлов и что именно изменено в каждом.
- Пояснение решений:
  - почему выбранный подход соответствует текущей архитектуре.
- Шаги проверки:
  - какие команды/проверки выполнены и их результат;
  - что не удалось проверить и почему (если есть).

## 3. Примеры типовых задач

### Сценарий 1: Добавление новой функции или endpoint
Пример промпта:
> Добавь endpoint для получения доступных комнат по интервалу времени и выведи этот фильтр на страницу списка комнат.

Ожидаемый формат ответа:
- план изменений (backend + frontend);
- список измененных файлов;
- описание API-контракта (query/body/response);
- результаты `dotnet build`, `npm run lint`, `npm run build`;
- краткая инструкция ручной проверки в UI.

Критерии готовности:
- endpoint работает и возвращает корректный набор комнат;
- frontend корректно вызывает endpoint и отображает результаты;
- существующая функциональность не сломана;
- сборка и линт проходят.

### Сценарий 2: Исправление бага по описанию
Пример промпта:
> Пользователь может удалить чужое бронирование. Исправь это и опиши причину бага.

Ожидаемый формат ответа:
- краткий root cause;
- конкретный фикс с ссылками на измененные файлы;
- проверка сценариев доступа (owner/admin/чужой пользователь);
- результаты команд проверки.

Критерии готовности:
- не-владелец без роли `Admin` получает запрет на удаление/изменение;
- владелец и админ сохраняют нужный доступ;
- нет регрессий в других методах `BookingsController`.

### Сценарий 3: Рефакторинг без изменения поведения
Пример промпта:
> Отрефактори `bookingsSlice` для улучшения читаемости, не меняя поведение.

Ожидаемый формат ответа:
- что и зачем рефакторилось;
- подтверждение, что API/поведение/типы не изменены;
- список проверок (lint/build) и их статус.

Критерии готовности:
- внешнее поведение и контракты остались прежними;
- код стал проще для поддержки (меньше дублирования, яснее структура);
- линт и сборка без ошибок.
